# Deep Dish — спецификация архитектуры (v1.1, 03.10.2026)

Домашний трекер питания и веса: PWA offline-first для семьи, синхронизация через NAS. Бюджет эксплуатации 0 ₽. Все решения ниже согласованы с В. (03.10.2026, PLAN.md v4).

## 1. Контуры системы

```
iPhone (PWA, offline-first)  ←→  [при появлении сети]  NAS TS-264C (Docker):
  IndexedDB (Dexie)                                        ├─ deep-dish-api (FastAPI + SQLite, WAL)
  Service Worker (Workbox)                                 ├─ caddy (HTTPS, внутренний CA)
                                                           ├─ headscale (координация сети)
                                                           └─ tailscaled (узел NAS в сети)
GitHub Pages — публичный хостинг фронтенда (статика).
Open Food Facts — внешний онлайн-справочник упакованных товаров.
Apple Health — через Shortcuts поверх API NAS (M3).
```

Принцип offline-first: весь функционал (ввод, правка, поиск, норма, графики, экспорт) работает без сети и без сервера неограниченно долго. Сервер — невидимый слой синхронизации; приложение полноценно и без него. Первый запуск не требует сервера. Единственное платформенное ограничение: самá установка PWA требует одноразового доступа к GitHub Pages.

## 2. Модель питания (по образцу MyFitnessPal)

Четыре сущности ввода:

1. **Продукт (food)** — атом: «Творог 9%». Поля: имя, бренд (опц.), категория, КБЖУ на 100 г, порция по умолчанию (граммы или «1 шт = 110 г»), штрихкод EAN-13 (опц.), источник (system | custom | off | fork).
2. **Рецепт (recipe)** — составное блюдо: список ингредиентов (продукт + граммы), выход готового (общий вес, г), порция по умолчанию. КБЖУ на 100 г готового пересчитывается из ингредиентов (с учётом потери/прибавки веса — выход задан руками). Съеденное = граммы или доля от выхода (1/3 кастрюли).
3. **Сохранённый приём пищи (saved meal)** — именованный набор продуктов с граммовками, вставляется в слот одним тапом («Мой завтрак»: овсянка 60 г + молоко 200 мл + банан). От рецепта отличается тем, что это просто макрос записей, ничего не пересчитывается.
4. **Запись дневника (entry)** — съеденное: ссылка на продукт/рецепт, граммы или порции, слот, дата, время приёма пищи, время создания записи (оба — решение В.), снапшот КБЖУ на момент ввода.

Правила каталога:
- Источники продуктов: встроенная база v2 (140 RU-позиций, `data/products_v2.json`), свои, импорт из OFF, fork чужих из семейного каталога.
- **Снапшот в записи**: правка/удаление продукта в каталоге не меняет прошлые записи дневника (поведение MFP).
- Быстрый ввод: недавние, частые, избранное (вычисляется из истории + ручной флаг).

Слоты приёмов пищи: расширяемые, дефолт — завтрак/обед/ужин/перекус; свои слоты пользователь добавляет и переименовывает. Дневники приватны per-user; каталог продуктов/рецептов общий для семьи (после M2).

## 3. Модель данных (единая для Dexie и SQLite)

Все синхронизируемые таблицы: первичный ключ `id` (UUIDv7 — сортируемый по времени), `createdAt`, `updatedAt`, `deletedAt` (tombstone; null = жива).

| Таблица | Ключевые поля |
|---|---|
| `foods` | name, brand, category, kcalPer100g, pPer100g, fPer100g, cPer100g, portionG, portionLabel, barcode, source, ownerId, isPublic |
| `recipes` | name, items: [{foodId, grams}], yieldG, (расчётные КБЖУ/100г кэшируются), ownerId, isPublic |
| `saved_meals` | name, items: [{foodId, grams}], slotHint, ownerId |
| `slots` | name, sortOrder, isDefault, defaultTime (HH:MM — автоподстановка при вводе; у перекуса — «сейчас»), ownerId |
| `entries` | userId, date (локальная YYYY-MM-DD), timeEaten (HH:MM — у каждой записи своё), slotId, kind: food\|recipe, refId, grams, snapshot: {kcal,p,f,c}, note |
| `weight_logs` | userId, date, weightKg, bodyFatPct?, source: manual\|health |
| `profiles` | userId, пол, возраст, рост, формула (mifflin\|katch\|manual), manualTdee?, активность, цель, темп кг/нед, цель веса |
| `norma_history` | userId, date, tdeeEstimate, targetKcal, method: formula\|adaptive, explanation (JSON для экрана «почему») |
| `users` (только сервер) | id, name, token, createdAt |

`ownerId = 'system'` — встроенная база v2 (read-only для всех). В M0 сервера нет: `userId` фиксированный локальный (`local`), при появлении синка маппится на серверный юзер.

## 4. Синхронизация (M2)

- Триггеры: открытие приложения, кнопка, появление сети (если включено).
- Протокол: один эндпоинт `POST /sync` — атомарный обмен. Запрос: `{ userId, since: <serverTime из прошлого ответа>, changes: [записи с updatedAt > lastSync] }`. Ответ: `{ changes: [...], serverTime }`. Часы клиента не участвуют (защита от перевода времени) — сервер отдаёт своё время, клиент хранит.
- Конфликты: last-write-wins по `updatedAt` (семейный сценарий: правки редки и не пересекаются).
- Удаления: tombstone (`deletedAt`), репликация и очистка старше 90 дней на сервере.
- Дневники: фильтр по `userId` — чужое не приходит.
- Каталог: приходят живые `foods/recipes` с `isPublic`; править можно только свои (`ownerId = я`); чужое — fork (копия со source=fork, ownerId=я).
- Идемпотентность: UUID-ключи позволяют повторить push после обрыва связи безопасно.

## 5. API NAS

Стек: FastAPI (Python) + SQLite (WAL, `PRAGMA synchronous=FULL` — электричество может пропасть в момент записи; файл на RAID-томе).

- `POST /sync` — см. §4.
- `GET /healthz` — живость (для мониторинга/shortcuts).
- Health-мост (M3, Shortcuts):
  - `GET /v1/weight/latest` — последний вес (shortcut: Find Health Samples → сравнить → POST новые);
  - `POST /v1/weight` — `{date, weightKg}` из Apple Health;
  - `GET /v1/calories/today` — сумма за день (shortcut: Log Health Sample, Dietary Energy).
- Админ-минимум: CLI-скрипт/страница за токеном администратора — создать юзера, выдать токен, отозвать.

Аутентификация: bearer-токен юзера (генерируется при создании юзера на сервере, вводится на устройстве в настройках один раз). TLS обязателен (см. §6).

## 6. Инфраструктура NAS

Container Station, docker-compose:

1. `headscale` — координационный сервер частной сети (решение В.: сразу, без лимита пользователей). Подключение устройств — по preauth-key.
2. `tailscaled` — узел самого NAS в этой сети.
3. `caddy` — HTTPS-прокси до API. Сертификат от **внутреннего CA Caddy** (публичного домена нет, LE не применим; DNS-имена вида `deepdish.<net>` резолвятся внутри сети). **Цена решения: root-CA Caddy один раз устанавливается профилем на каждом устройстве семьи** (iOS: Настройки → Профиль → доверие). Без этого Safari/PWA не примут сертификат.
4. `deep-dish-api` — приложение; SQLite-файл в volume на RAID.

Безопасность: из публичного интернета не выставлено ничего (Headscale-контроль — только внутри, ключи выдаёт В.; если нужен внешний вход для первого подключения — точечный проброс UDP или ручной режим). Админка QTS в сеть не торчит. Бэкапы: HBS3 ежедневно копирует volume с SQLite на второй том/внешний диск.

Отказоустойчивость: NAS выключен/нет света → приложение полноценно работает локально, синк догонит; SQLite в WAL переживает внезапное отключение питания; контейнеры с `restart: unless-stopped`.

PWA и mixed content: фронт на GitHub Pages (HTTPS) зовёт API по HTTPS внутреннего CA — после установки CA-профиля работает. Резервный вариант при проблемах: зеркало фронтенда на самом Caddy (same-origin).

## 7. Норма калорий

- Старт: формула на выбор — Миффлин–Сан Жеор / Кэтч–МакАрдл (если введён % жира) / ручной TDEE; + цель (похудение/поддержание/набор) и темп (кг/нед).
- Адаптация (через ≥14 дней данных, окно 14 дней, сдвиг 7 дней): TDEE_факт = среднее потребление ккал/день + 7700 × (−тренд веса кг/день); тренд веса — линейная регрессия по логу веса за окно.
- Цель = TDEE_факт ± дефицит/профицит из темпа; ограничители: изменение цели ≤150 ккал/нед; не ниже 1,1 × BMR.
- Каждое изменение нормы — строка в `norma_history` с объяснением (компоненты расчёта) для экрана «почему такая цифра».

## 8. Фронтенд

- Стек: React 18 + TypeScript + Vite; Tailwind (дизайн-токены, тёмная/светлая темы); Dexie над IndexedDB, миграции версий схемы; vite-plugin-pwa (Workbox precache, `skipWaiting` + явный тост «доступна новая версия — применить»).
- **Офлайн-загрузка — жёсткое требование (урок v2: «нет интернета — нет приложения»; у v2 fetch-хендлер был network-first для внешних ресурсов, шрифты шли с Google Fonts, precache — неполный)**:
  - Workbox precache ВСЕГО бандла атомарно (HTML, JS, CSS, иконки, манифест, шрифты) — установка SW считается успешной только после полного кэша;
  - `navigateFallback` на index.html — навигационный запрос всегда отвечает из кэша, сеть не нужна для запуска;
  - шрифты — системный стек с `-apple-system` первым (на iOS это San Francisco Pro; решение В. 03.10): лицензионно чисто на платформах Apple, нативные Optical Sizes и табличные цифры, **ноль сетевых загрузок**; внешних CDN в рантайме нет вообще;
  - установка на «Домой» (иконка) — рекомендуемый режим: home-screen приложения исключены из 7-дневной чистки хранилища iOS;
  - приёмочный тест каждого релиза: iPhone в авиарежиме → холодный запуск PWA → полный функционал.
- Экраны (M0): Сегодня (слоты, итоги, кольцо калорий) · Добавление (поиск, недавние/частые/избранные, OFF — с M2) · Продукт/Рецепт (карточка, граммы/порции) · Редактор рецепта · Рецепты/Сохранённые приёмы · История (день: правка/удаление/копирование) · Вес и норма (M1) · Профиль · Настройки (подключение синка, экспорт JSON/CSV, сброс).
- Деплой: GitHub Actions → GitHub Pages (ветка main). Версия приложения + git SHA в «О приложении».
- Русский язык; единицы кг/см/ккал; safe-area iOS; inputMode numeric везде, где числа.
- **Дизайн-язык (бриф В. 03.10, развитие 05.10):** воздушный интерфейс — пространство вместо линий (разделение отступами, не рамками); **радиальные градиенты по углам поверх линейного перелива фона** (как в презентации BHC; интенсивность — на выборе В. из 0/×1/×2, витрина design/gradients.html); у каждого экрана свой пресет позиций/масштабов пятен, при переходах — плавный кросс-фейд фонового слоя (~300 мс); акценты градиентом от основного тона к светлому (кольцо, точки слотов, вуаль действий, кромка баннеров); карточки — «стекло» (полупрозрачное размытие поверх градиента), обводок нет; действий без «кнопочности» — тонкая заливка акцентом с текстом цвета акцента. Эмодзи — сдержанно, выборочно (не больше одного на блок; обязательны в баннерах).
- **Токены гаммы «Графит·сталь» (утверждена В. 04.10):**
  - светлая: фон-градиент #F5F6F8→#ECF0F4, стекло rgba(255,255,255,.60), текст #1B2026, вторичный #8B929C, акцент-градиент #44748F→#6E9BBB, вуаль действий rgba(68,116,143,.10), трек rgba(27,32,38,.07);
  - тёмная: фон-градиент #14171B→#191E26, стекло rgba(255,255,255,.065), текст #E9EDF2, вторичный #969DAA, акцент-градиент #7FA8C9→#AECBE2, вуаль rgba(127,168,201,.12), трек rgba(255,255,255,.09);
  - семантические поверх гаммы: «превышение» — тёплый красный, «в норме» — зелёный; фирменный мотив — кольцо (иконка И4, кольцо калорий, прогресс цели).
- **Выбор гаммы в настройках** (В. 04.10): Графит·сталь (дефолт) + Лазурь + Индиго + Брусника + Матча — наборы токенов обеих тем; настройка пер-устройственная (не синхронизируется); иконка приложения всегда графитовая.

### Экран добавления еды (В. 04.10)

Поле поиска сверху → **«Недавние»** → **«Проверенные ⭐»** → **«Каталог»** (по категориям). Все секции сворачиваемые (состояние свёрнутости запоминается). При вводе текста — единый отфильтрованный список. «Проверенное ⭐» — одна пометка на две роли: быстрый доступ + личное доверие к КБЖУ (снимается/ставится одним тапом на карточке продукта/рецепта). Поиск полностью офлайн (локальная база в IndexedDB: встроенная + свои + рецепты + семейный каталог после синка); без сети просто нет секции «Open Food Facts».

### Проверка КБЖУ при вводе (В. 04.10)

- Всегда (офлайн): эвристика энергетического баланса 4/4/9 — расхождение >25% → вопрос; алкоголь — особый случай (ккал из спирта, 7 ккал/г; keyword-детект «вино/пиво/водка/…»).
- При онлайне: сверка с Open Food Facts по похожему названию (порог ~±25%).
- При расхождении: popup при сохранении («Похожий продукт: 89 ккал, у вас 350 — проверить?» / «Сохранить как есть» / «Исправить») + постоянная пометка ⚠️ у карточки в списках выбора. Отдельный баннер не используется.
- Пометка ⚠️ также наследуется семейным каталогом (чужие записи с флагом видны всем).

## 9. Онбординг и мотивационные баннеры (решения В. 04.10; детали баннеров — на уточнении)

**Онбординг** (первый запуск, 3–4 шага, всё пропускаемо):
1. Приветствие: что это и главный принцип — ввод еды за секунды.
2. «Как пользоваться»: где искать продукты, как добавлять запись, рецепты, копирование дня.
3. Профиль и цель (опционально): биометрия → формула или ручной TDEE → цель и темп. Режимы: без профиля (просто дневник) / профиль без цели (норма) / с целью (норма + динамика + баннеры). v2-проблема «странных целей» закрыта адаптивной нормой + экраном «почему такая цифра».
4. Готово + установка на «Домой» подсказкой.

**Время еды — атрибут каждой записи** (ревизия В. 05.10): каждая запись несёт собственное `timeEaten`; слот — группировка, не контейнер времени. Автоподстановка: завтрак/обед/ужин — дефолт слота (из настроек), перекус — текущее время; время видно в списке у каждой записи и правится в карточке (рядом с граммами, тот же шит). `createdAt` — служебное, в интерфейсе не отображается. Дефолты времён слотов в настройках остаются как ускоритель ввода.

**Мотивационные баннеры** (элемент дизайна приложения, НЕ пуши — решение В. 04.10; только при активной цели):
- Вида: выезжающая панель-«top sheet» сверху; видна на всех экранах, пока не закрыта крестиком; сама исчезает после нескольких пользовательских действий (навигация/ввод); часовая зона — устройства.
- Тип А «по плану/быстрее»: при утреннем открытии до ~12:00 местного; «Так держать! такими темпами через Х недель — Y кг»; 1 показ/день.
- Тип Б «предостережение»: с **упреждением ~1 час до начала окна срывов** и до его конца (В. 05.10: в само окно пользователь может не открыть приложение); прямой тон; не одновременно с типом А; 1 показ/день.
- Тексты: 3 дерзких + 2 нейтральных на тип (ротация); эмодзи обязательно; два независимых тумблера в настройках.

**Окно срывов** — по категориям угощения, а не по превышению нормы (правка В. 04.10):
- «Красные флаги» — настраиваемый набор категорий, дефолт: Сладкое, Фастфуд, Снеки, Алкоголь (+ свои категории пользователя).
- Паттерн: скользящее окно 2 ч; вхождение = запись из флаг-категории в этом окне дня; окно «риска» — если ≥3 вхождения за последние 14 дней (защита от ложных паттернов: меньше данных — баннер не показывается).
- Существенно: триггер — сама связка «время × угощение», даже если дневная норма не превышена (пример: полбутылки вина каждый день в 10:00 — превышения может не быть, аномалия налицо).

**Категоризация продуктов/рецептов — три эшелона** (кто раскладывает по категориям):
1. Основной, автоматический почти всегда: категория обязательна при создании своего продукта/рецепта (выбор из списка с дефолтом-подсказкой); при сохранении из Open Food Facts категория приходит сама (маппинг их тегов на наш список); встроенная база v2 уже с категориями.
2. Офлайн-правила: keyword-классификатор по названию («торт», «вино», «чипсы» → флаг-категория) для позиций «без категории»; работает на телефоне, без сети.
3. ML на NAS (M3, второй эшелон): батчевая классификация накопленного «без категории» — мини-модель по названиям (мультязычная sentence-embedding + kNN по нашей базе); Google Coral TPU на NAS для этой задачи избыточен (инференс миллисекунды на CPU); Coral остаётся в резерве как ML-ускоритель NAS для будущих серверных задач (В. 04.10: ресурс учитываем, фото-еда — не его случай).

### Продуктовые метрики (решение В. 04.10: обвязать приложение и анализировать)

- **Сбор с первого дня (M0)**: локальный журнал событий в отдельной таблице Dexie (`events`: id, userId, ts, session, name, props JSON). Логгер — тонкая функция `track(name, props)`, вызывается из кода экранов. Офлайн — копится без ограничений.
- **Транспорт (M2)**: события едут попутно тем же обменом `POST /sync` (отдельный эндпоинт не нужен) — в changes добавляется ветка events; сервер складывает их в таблицу SQLite `events`. Досыл после любого офлайна автоматический.
- **Приватность**: события не содержат содержимого дневника — только обезличенные действия (названия продуктов/блюд/вес НЕ пишутся). Метрики живут дома на NAS, наружу не уходят. Отключение — тумблер в настройках (по умолчанию включено, о нём сказано в онбординге).
- **Состав событий**: `app_open` (online/offline, cold/warm) · `onboarding_step` (шаг, drop-off) · `entry_added` (источник: поиск/недавние/проверенные/каталог/копирование дня; время от открытия до записи — ключевая метрика «ввод за секунды») · `food_created/edited` (флаг «КБЖУ под вопросом» — сработала ли проверка) · `recipe_created` · `star_toggled` · `banner_shown/closed/autodismissed` (тип, вариант текста) · `export_done` · `sync_result` (ok/fail, латентность) · `js_error`.
- **Витрина (M2)**: страница-отчёт в приложении (доступна В.): вовлечённость по дням/юзерам, регулярность записей, медианное время ввода, использование функций, показы/закрытия баннеров, доля офлайн-сессий. Рендер — свои средства (лёгкие SVG-графики, без сторонних библиотек).
- **A/B (В. заинтересовался)**: механика — детерминированное распределение вариантов `hash(userId+experiment)` + событие exposure; тексты баннеров (3 дерзких/2 нейтральных) ротируются с записью варианта. **Честная оговорка: при 2–5 пользователях классический A/B статистически не значим** — используем как n=1/n-семьи эксперименты (ротация + индивидуальный замер реакции: закрыл/не закрыл, изменилось ли поведение после показа), выводы формулирует агент с явной пометкой о малой выборке.
- **Анализ**: по запросу В. агент прогоняет агрегаты по SQLite и делает разбор (тренды, аномалии, гипотезы).

### Обмен результатами между пользователями (идея В. 04.10; варианты на выборе)

Суть: обмен агрегированными отчётами (тренд веса, % дней с записями, adherence к норме, прогресс к цели) — без содержимого дневника. Получение — top-sheet-уведомление «💬 В. поделился результатами за неделю: −0,4 кг, 85% дней с записями», авто-скрытие через 3 действия, как баннеры.

**Утверждённая модель (В. 05.10):**
- Отправитель: в настройках «Видимость моих результатов» — вкл/выкл + уровень детализации (полный: тренд веса, регулярность, прогресс к цели / «без веса»: регулярность и прогресс в %). Уведомляется о новых подписках.
- Получатель: «Подписки» — выбор одного или нескольких пользователей; недельная авто-сводка приходит top-sheet-уведомлением (авто-скрытие через 3 действия, как баннеры).
- Разовая отправка: кнопка «поделиться результатом» в своём отчёте → выбор получателя → однократная отправка.
- Челлендж-режим — отложен (записан в идеи на будущее).
- Данные: таблица `shared_reports` (fromUser, toUser, period, payload JSON, createdAt, readAt); агрегаты считает сервер (M2+). Реализация — M3.

### CJM: частотные операции и целевая длина пути (В. 04.10)

| Операция | Частота | Цель (тапы) | Путь |
|---|---|---|---|
| Повторная запись (то же, что ел) | самая частотная | **≤2** | слот → «+» на карточке в «Недавних» → предзаполненный шит граммов (последняя порция) → «Сохранить»; поправить вес = тот же шит (В. 05.10: порции редко грамм-в-грамм) |
| Новая запись из каталога | частая | 4 | слот → поиск/раздел → карточка → граммы (предзаполнены) → сохранить |
| Глянуть остаток дня | постоянная | **0** | всегда на «Сегодня» |
| Просмотр другого дня | ежедневная | 0–1 | свайп влево/вправо на «Сегодня»; стрелки ‹ ›; тап по дате — календарь (копирование дня исключено, В. 05.10) |
| Правка записи | редкая | 3 | запись → «изменить» → граммы → сохранить |
| Внести вес | ежедневная | — | основной путь: умные весы → Apple Health → приложение (M3); до моста — ручной ввод в экране веса (временный fallback, после моста прячется, В. 05.10) |

Принципы: все поля предзаполнены дефолтами (последняя порция), после сохранения — возврат туда, откуда пришёл; каждый экран проходит UX-аудит (зачем элемент, сколько тапов до ценности) перед вёрсткой.

## 10. Экспорт/импорт

- Полный JSON-бэкап всех локальных таблиц (одной кнопкой, файл `deepdish-backup-YYYYMMDD.json`); восстановление из файла.
- CSV: `entries` (дата, время, слот, блюдо, граммы, ккал, Б/Ж/У) и `weight_logs`.
- Импорт CSV не входит в объём (MFP-миграция исключена решением В.).

### Роли (В. 05.10)

Единое приложение у всех; роли на сервере: `admin` (В.) — создание/отзыв юзеров и токенов, семейная витрина метрик; `member` — свои дневник и метрики, подписки/обмен на общих основаниях.

### MyFitnessPal-импорт — возвращён как опция (В. 05.10)

Через 7-дневный Premium-триал MFP доступен полный CSV-экспорт (еда-по-приёмам, вес, упражнения). Переход — после M2 (В. 05.10): до импорта основной учёт в MFP, в DD — тестовые записи; после импорта DD становится основным инструментом. Сценарий: команда-инструкция от агента → триал (оплата — турецкий Apple ID) → выгрузка CSV → парсер импортирует историю → тестовые записи DD до даты импорта удаляются функцией «очистить дневник до даты» (с подтверждением и предварительным экспортом). Отмена подписки до списания — ответственность В.

### LLM-анализ периодов (В. 05.10, M3+)

Периодическая выгрузка данных за период (и ретроспектива на всю глубину) и разбор агентом: динамика, паттерны, аномалии — поверх метрик и SQLite на NAS. LLM-вызовы в само приложение не встраиваются. Отчёты — в Obsidian и/или общим отчётом в приложении.

### Онбординг: манипуляции с телефоном (В. 05.10)

Блок «настройка устройства» внутри онбординга, пополняется по итерациям: M0 — «На экран Домой»; M2 — установка CA-профиля и подключение к серверу; M3 — настройка Health-команд. Пошагово, с галочками выполнения.

## 11. Риски и компромиссы (честный список)

1. **CA-профилический HTTPS** — разовая ручная операция на каждом устройстве; при смене устройства/переустановке Caddy — повторить. Альтернатива (платный домен + публичный LE) отвергнута бюджетом 0 ₽.
2. **LWW-конфликты** — одновременная правка одной записи с двух устройств теряет более старую правку. Для семьи с приватными дневниками практически нереализуемо; каталог закрывается fork-моделью.
3. **OFF охват RU** — замерим фактически на M2 (ожидание: упакованные хорошо, домашняя кухня — нет; её закрывает база v2 + рецепты).
4. **Health-мост — полуавтомат через Shortcuts** (запуск вручную или автоматизация по расписанию/триггеру); прямой интеграции не существует.
5. **Сканер штрихкодов** — нативного API в iOS Safari нет; JS-сканер — эксперимент M3, не обещание.
6. **GitHub Pages зависим** — недоступность Pages влияет только на первичную установку и обновления; уже установленное приложение (офлайн-кэш) работает независимо.
7. **Первый вход в Headscale вне дома** — нужен одноразовый доступ к координационному серверу; продумаем на M2 (точечный проброс или установка только из дома).
